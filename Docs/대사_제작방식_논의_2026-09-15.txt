[아이디어 논의]
# 목표
현재 프로젝트의 제작 방향성 고민.
현재 프로젝트를 분석하고 프로젝트의 방향성에 맞는 대사 작업 방식을 제시한다.

# 프로젝트 배경
- 대규모 텍스트 기반 선택지 시스템
- 플레이어의 능력치, 선택지 조건에 따른 분기 시스템 존재
- 캐릭터 이미지 연출, BGM, 효과음 기능 존재

# 완료 조건
1. 기존의 프로젝트 구조와 기능을 분석한다.
2. '프로젝트 배경'에 맞는 기능을 구현하고 1인 개발자가 홀로 스크립트를 쓰고 에셋 작업을 한다고 할 때 현재 구조대로 그래프 중심으로 대사를 작성하는 것이 유지보수 및 1인 작업에 수월할지, 엑셀이나 스프레드시트 등을 이용하는 것이 1인 작업 및 유지보수에 수월할지 분석 및 제시한다.

이번 작업에서 코드 수정 또는 파일 수정은 절대 하지 않는다.
오로지 분석 및 보고만 한다.

3. 최종 분석 보고
======================================================================

■ 결론

목표로 하신 “대규모 텍스트·조건부 선택지·캐릭터 및 사운드 연출”을 1인이 제작한다면, 장기적으로는 스프레드시트 중심 집필이 더 적합합니다. 그래프는 분기 구조를 확인하고, Unreal에서는 연출을 조정·확인하는 역할을 맡기는 방향을 권합니다.

다만 현재 구현 그대로 당장 제작한다면 그래프 중심이 현실적입니다. 현재의 CSV 기능은 지역화용 문구 입출력이며, 시트에서 대사·조건·연결·연출을 작성해 원본 그래프에 반영하는 기능은 아닙니다.

따라서 제안은 다음과 같습니다.

단기: 현재 그래프로 장면 제작
장기: 시트를 원고의 기준으로 삼고 기존 런타임·그래프를 활용하는 저작 기능 확장

아래 생산성 평가는 코드 구조를 바탕으로 한 판단이며, 실제 집필 시간이나 대규모 그래프 성능을 측정한 결과는 아닙니다.

----------------------------------------------------------------------
3-1. 현재 프로젝트 구조와 기능
----------------------------------------------------------------------

DialogueMaker는 DialogueKit 플러그인에 실제 기능이 집중되어 있고, Runtime과 Editor 모듈이 분리되어 있습니다.

[대사 작성과 실행 구조]

그래프 에디터
  └─ 노드 선택 → Details에서 본문·선택지·연출 수정
          ↓ 저장
UDialogueGraph
  └─ UDialogueRuntimeGraph
       └─ 노드·핀 ID / 연결 / NodeInfo
          ↓
UDialogueSubsystem에서 대화 진행

편집 그래프와 런타임 그래프 사이의 변환이 이미 존재합니다. 현재 실행 구조를 유지하면서 작성 방식을 추가할 여지가 있다는 점은 장점입니다.
근거: Plugins/DialogueKit/Source/DialogueKitEditor/Private/DialogueGraphEditor.cpp:105

1) 대사
   현재 구조: 한 대사 노드에 본문, 화자, 선택지, 초상화 정보, 연출 배열 저장.
   제작 의미: 한 장면의 문구와 연출을 함께 조정하기 편함.

2) 대화 후보 선택
   현재 구조: 화자, 태그 조건, 대화 종류·우선순위 관련 구조.
   제작 의미: 상황에 맞는 대화를 고르는 기반 존재.

3) 선택지·분기
   현재 구조: 최소 플레이어 레벨과 GameplayTagQuery 평가.
   제작 의미: 조건 분기 기반은 있으나 임의 능력치 비교까지 일반화된 구조는 아님.

4) 선택 결과
   현재 구조: 선택지 자체에는 효과 목록이 없고, 일반 종료 노드에서 태그 추가 처리.
   제작 의미: 호감도 증가·아이템 지급 등 범용 결과 효과는 별도 확장 필요.

5) 캐릭터 연출
   현재 구조: 화자·표정에 따른 이미지 자산, 노드별 연출 배열, Move·Flip 실행 경로.
   제작 의미: 에셋 재사용 기반은 있으나 세부 연출값은 노드별 작성 부담 발생.

6) 저장
   현재 구조: 대화 자산 ID와 노드 GUID 기반 표시 이력.
   제작 의미: 작성 도구를 바꿔도 기존 ID 보존이 중요.

7) CSV
   현재 구조: 본문·선택지 문구 추출 및 별도 지역화 자산 생성.
   제작 의미: 전체 대사 저작용 시트와는 범위가 다름.

- Plugins/DialogueKit/Source/DialogueKit/Public/Struct/DialogueStructure.h:9
- Plugins/DialogueKit/Source/DialogueKit/Private/DialogueSubsystem.cpp:248
- Plugins/DialogueKit/Source/DialogueKit/Public/ShownDialogueSaveData.h:15

[프로젝트 배경과 구분할 부분]

사용자께서 제시한 기능을 최종 제작 요구로 반영하되, 현재 구현의 완성 범위는 구분해야 합니다.

- 능력치: 확인한 공통 조건은 최소 레벨과 태그 쿼리입니다. “매력 ≥ 20”, “호감도 < 50” 같은 임의 능력치 비교가 범용적으로 구현되었다고 보기는 어렵습니다.
- 선택지 표시: 확인한 C++ 경로는 조건을 만족하지 못하는 선택지를 목록에서 제외합니다. “보이지만 선택 불가능” 처리는 Blueprint UI 확인이 필요합니다.
- BGM·효과음: 조사한 C++에는 대사 노드의 사운드 데이터나 재생 경로가 확인되지 않았습니다. Blueprint 내부는 확인하지 않았으므로 기능 부재로 단정하지 않습니다.
- 연출: Move·Flip 실행 코드는 있지만, ActionSequencer의 Emote 분기는 비어 있습니다. 모든 연출 종류가 완성된 상태로 가정하지 않았습니다.
  근거: Plugins/DialogueKit/Source/DialogueKit/Private/ActionSequencer.cpp:183

작성 도구 선택과 함께, 조건·결과·연출을 어디까지 데이터로 표현할지 정하는 일이 필요합니다.

----------------------------------------------------------------------
3-2. 그래프와 스프레드시트 비교
----------------------------------------------------------------------

시트 중심 방식은 적절한 가져오기 기능을 갖춘 경우를 전제로 비교했습니다.

1) 긴 대사 연속 집필
   현재 그래프: 노드 생성·선택·연결 작업이 반복됨.
   시트 중심: 행을 이어 쓰며 집필하기 유리.

2) 전체 퇴고·용어 통일
   현재 그래프: 여러 노드·자산을 오가야 함.
   시트 중심: 검색·필터·일괄 수정에 유리.

3) 분기·합류 파악
   현재 그래프: 연결선으로 파악하기 유리.
   시트 중심: 목적지 ID만으로는 추적이 번거로움.

4) 조건 수치 일괄 조정
   현재 그래프: 노드별 속성 접근 필요.
   시트 중심: 조건별 목록 비교·수정에 유리.

5) 세부 연출 입력
   현재 그래프: Unreal의 자산·속성 편집 활용 가능.
   시트 중심: 복잡한 연출 배열을 셀에 적으면 불편.

6) 실제 연출 확인
   현재 그래프: Unreal 재생 확인 필요.
   시트 중심: 가져온 뒤 Unreal 재생 확인 필요.

7) 변경 이력
   현재 그래프: .uasset만으로 문구 변경을 읽기 어려움.
   시트 중심: CSV 등 텍스트 산출물을 버전 관리하면 유리.

8) 도구 유지보수
   현재 그래프: 기존 도구 활용 비용이 낮음.
   시트 중심: 가져오기·검증 기능 개발 비용 발생.

[그래프가 특히 유리한 경우]

대사량보다 장면마다 다른 분기와 세밀한 연출의 비중이 높은 경우입니다. 짧은 장면에서 선택지의 목적지를 연결하고 연출값을 조정하는 작업은 현재 구조와 잘 맞습니다.

[이번 목표에서 시트가 유리한 이유]

대규모 텍스트 프로젝트에서는 최초 입력 이후에도 다음 작업이 반복됩니다.

- 캐릭터 말투와 설정 통일
- 앞 장면 변경에 따른 후속 대사 수정
- 조건별 선택지 문구 비교
- 미작성·미검수·에셋 미완료 항목 확인
- 번역 및 오탈자 수정

이 작업들은 연결선을 편집하는 시간보다 문장을 읽고 비교하는 시간이 중심입니다. 혼자 집필과 에셋 제작을 병행한다면, 일괄 작업과 작업 상태 파악이 쉬운 편이 유리합니다.

다만 시트에 복잡한 조건식·연출 배열·에셋 경로를 모두 직접 입력하게 만들면 그 이점이 줄어듭니다. 시트 자체보다 시트를 얼마나 단순하게 설계하느냐가 중요합니다.

----------------------------------------------------------------------
3-3. 현재 CSV를 그대로 집필 도구로 쓰기 어려운 이유
----------------------------------------------------------------------

현재 CSV의 주요 열은 다음과 같습니다.

NodeGuid, PinId, Key, Value

내보내는 내용은 대화 자산 식별자와 본문·선택지 문구이며, 다음 정보는 포함되지 않습니다.

- 화자와 장면 맥락
- 다음 노드 연결
- 선택지·분기 조건
- 선택 결과 효과
- 캐릭터 연출

또한 가져오기는 원본 그래프를 수정하지 않고 별도 DialogueLocalizationDataAsset을 생성·갱신합니다.
근거:
- Plugins/DialogueKit/Source/DialogueKitEditor/Private/DialogueLocalizationCSVConverter.cpp:333
- Plugins/DialogueKit/Source/DialogueKitEditor/Private/DialogueLocalizationCSVConverter.cpp:384

즉, 현재 기능은 기존 문구를 목록으로 검토하거나 번역하는 용도에 맞습니다. 여기서 새 대사를 행으로 추가한다고 실행 노드가 생성되지는 않습니다.

Unreal의 일반 DataTable CSV 가져오기도 정해진 행 구조가 필요합니다. 현재의 UObject 노드·핀 연결까지 자동으로 변환해 주는 기능으로 볼 수 없습니다.
Epic 공식 UE 5.4 문서:
https://dev.epicgames.com/documentation/en-us/unreal-engine/data-driven-gameplay-elements-in-unreal-engine?application_version=5.4

3-4. 권장하는 최종 작업 방식
----------------------------------------------------------------------

[역할 분담]

- 본문·화자·선택지 문구: 시트를 기준으로 편집.
- 조건·결과·연결 대상: 시트에서 지정된 항목 선택.
- 재사용할 캐릭터·사운드·연출 설정: Unreal 자산을 기준으로 편집.
- 분기 구조 검토: 시트 데이터에서 생성한 그래프 사용.
- 연출 타이밍·스킵·실제 화면 검토: Unreal 재생.

같은 문구와 연결을 시트와 그래프 양쪽에서 자유롭게 고치는 방식은 초기에는 피하는 편이 좋습니다. 재가져오기 때 어느 쪽 변경을 유지할지 판단하는 도구까지 혼자 관리해야 하기 때문입니다.

시트가 기준이라면 그래프는 구조 확인용으로 두고, 연출 자산은 Unreal에서 수정하는 식으로 데이터별 편집 위치를 정하는 편이 단순합니다.

[시트는 크게 세 종류면 충분합니다]

아래는 향후 저작 형식의 예시이며, 현재 CSV 형식은 아닙니다.

1) 대사 시트
   장면 ID, 대사 ID, 표시 순서, 화자, 본문, 다음 대사 ID, 연출 ID.

2) 선택지 시트
   선택지 ID, 소속 대사 ID, 문구, 조건 ID, 결과 ID, 이동 대상 ID.

3) 제작 관리 시트
   장면 ID, 집필 상태, 검수 상태, 필요한 이미지·사운드, 메모.

조건과 연출은 반복해서 쓰는 내용을 이름으로 참조하도록 만드는 것이 좋습니다.

예를 들어 집필 중에는 “왼쪽 등장_기본”을 선택하고, 실제 이동 시간과 위치는 Unreal의 해당 연출 설정에서 관리합니다. 등장 속도를 바꿀 때 대사 수십 곳을 수정하지 않아도 되는 구조가 1인 작업에 유리합니다.

복잡한 복수 액션은 별도 연출 데이터에서 다루고, 대사 시트에 수많은 타이밍 열을 늘리는 방식은 피하는 것을 권합니다.

[전환에 필요한 핵심 기능]

우선순위는 화려한 편집 UI보다 다음 항목입니다.

1) 안정적인 ID와 재가져오기
   - 문구 수정·행 정렬 시 노드와 선택지 ID 유지.
   - 기존 표시 이력·지역화 키와의 연결 보존.
   - 행 번호를 영구 ID로 사용하지 않기.

2) 가져오기 전 오류 검사
   - 중복 ID, 없는 목적지, 잘못된 조건·연출 참조 확인.
   - 선택지 순서가 바뀌어도 연결 대상 유지.
   - 기존 데이터에 반영될 변경 내용을 미리 표시.

3) 반복 조건·연출 재사용
   - 조건과 결과 효과를 일정한 형식으로 정의.
   - 자주 쓰는 연출을 재사용 가능한 설정으로 관리.

현재 선택지와 출력 핀은 배열 순서에 의존하는 부분이 있으므로, 선택지 재정렬의 안정성은 시트 전환 전에 확인할 항목입니다. 코드상 위험을 확인했으며 실제 오동작을 재현한 것은 아닙니다.

----------------------------------------------------------------------
3-5. 현실적인 제작 방향
----------------------------------------------------------------------

[지금 바로 콘텐츠를 만들어야 한다면]

현재 그래프를 원본으로 유지하는 편이 낫습니다.

- 하나의 거대한 그래프보다 독립적으로 검토할 수 있는 장면 단위로 관리합니다.
- CSV는 문구 목록 검토·번역에 사용합니다.
- 원본 문구 수정은 그래프에 반영합니다.
- 시트에는 장면별 집필·에셋·검수 진행 상태를 관리합니다.

이 단계에서 모든 대사를 별도 시트에도 수작업으로 복제하면 이중 관리 부담이 생깁니다.

[본격적인 대량 집필 전에 도구를 개선할 수 있다면]

시트 중심 저작으로 발전시키는 쪽을 권합니다. 기존 런타임 그래프를 출력 대상으로 활용하면 실행 시스템 전체를 바꾸는 부담을 줄일 수 있습니다.

전환 범위를 정할 때는 대표 장면 하나를 기준으로 다음 작업을 비교하면 좋습니다.

- 대사 여러 줄 추가·삭제
- 선택지 순서와 목적지 변경
- 조건값 일괄 수정
- 반복 연출 수정
- 수정 후 게임에서 확인하기까지 걸리는 시간

핵심 판단 기준은 최초 집필 속도보다 수정 후 다시 확인하는 데 드는 시간입니다.

또한 1인 제작에서는 도구와 별개로, 짧은 선택 분기 후 공통 흐름으로 합류하고 중요한 선택만 장기 분기로 남기는 방식이 콘텐츠·에셋·검수량을 관리하기 쉽습니다. 그래프나 시트를 바꾸어도 계속 갈라지는 이야기의 제작량 자체는 줄어들지 않습니다.

----------------------------------------------------------------------
3-6. 최종 판단
----------------------------------------------------------------------

DialogueMaker는 그래프 기반 실행 구조를 유지하면서, 대량 집필을 위한 시트 저작 기능을 추가하는 방향이 가장 적합합니다.

현재 그래프는 짧은 장면의 분기·연출 제작에 유용합니다. 다만 목표한 규모에서는 시트에서 집필하고, 그래프로 흐름을 확인하며, Unreal에서 연출을 관리하는 방식이 장기 유지보수에 더 유리하다고 판단합니다. 그 전제는 안정적인 ID, 검증 가능한 재가져오기, 데이터별 단일 원본입니다.

[분석 당시 조사 범위]

- DialogueMaker의 현재 작업 트리 기준으로 분석했습니다.
- Sol Medium 검토자와 Luna High 조사자의 읽기 전용 결과를 취합했습니다.
- 분석 단계에서는 코드·파일 수정은 하지 않았습니다.
- 에디터 실행·빌드·테스트는 수행하지 않았으며, Blueprint 내부 동작과 실제 대규모 작업 성능은 미검증입니다.
