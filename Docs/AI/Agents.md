# UE 에이전트 팀 운영 절차

## 자동 적용 원칙 (사용자의 상시 위임 지시)

- 이 절차는 메인이 프로젝트 작업 요청을 받을 때마다 기본으로 적용한다. 사용자가 매번 “실제 하위에게 조사·검토를 맡기고 결과 취합 후 메인만 수정해”라고 반복할 필요가 없으며, 위임 자체의 재승인을 요청하지 않는다.
- 코드 조사·리뷰·기능 개발·버그 수정에서 필요한 독립 조사·검토를 메인이 식별하고, 적합한 역할의 실제 하위를 생성한다. 역할극으로 대신하지 않는다. 질문·범위·인원은 요청에 맞게 정하며, 독립적으로 맡길 일이 없는데 형식적으로 인원을 채우지 않는다.
- 이 자동 위임 지시는 메인에게 적용한다. 하위는 맡은 범위에서 읽기 전용으로 조사·검토하며 추가 하위를 생성하지 않는다.
- 관련 하위 결과를 모두 취합하고 사실·추정·모순을 확인한 뒤 메인만 수정한다. 조사/설명/리뷰만 요청한 경우에는 취합·보고로 끝내며 구현·빌드·테스트로 범위를 확대하지 않는다.
- 이번 요청의 명시적인 하위 사용 금지·역할 지정·수정 금지 등은 이 기본 절차보다 우선한다. 사소한 문서/오탈자 또는 독립적으로 맡길 작업이 없으면 메인이 처리하고 생략 이유를 짧게 보고한다.
- 기존 역할별 모델·추론 수준, 메인 제외 하위 동시 3개 한도, 모델 임의 대체 금지, 사용자 확인 조건을 유지한다. 하위 위임의 상시 요청은 저장 형식 변경·에셋 삭제/이름 변경·엔진/새 외부 플러그인·범위 밖 재설계의 승인을 뜻하지 않는다.

## 역할
- Main/Lead: gpt-6-astra, medium. 사용자 요청 해석, 범위/작업 배분, 결과 검증, 실제 구현과 최종 판단.
- ue_senior_reviewer: gpt-5.6-sol, medium. C++/UE 구조 검토. 독립 주제별 동일 역할 인스턴스 여러 개 사용 가능.
- ue_research_scout: gpt-5.6-luna, high. 요청에 필요한 코드·설정·문서·기존 로그 탐색과 사실 조사.
- ue_deep_reviewer: gpt-5.6-sol, high. 어려운 버그, 반복 실패, 재현 불확실성, 검토 충돌일 때만 선택 호출.
- 메인 제외 동시 3개. Sol Medium 2개 + Luna High 1개가 가능하다. Sol High는 완료된 작업 슬롯을 재사용한다.
- 역할은 역량과 책임을 정의한다. 담당 기능·질문·조사 범위·필요 인원은 Astra가 현재 요청에 따라 정한다. 특정 시스템을 고정 담당하지 않으며 Sol 2개 + Luna 1개도 가능한 구성의 예시다.

## 메인 작업 흐름
사용자 요청 → 관련 코드 탐색 → 문제 범위 결정 → 서브에이전트 작업 배분 → 결과 취합 → 구현 → 빌드 → 오류 분석 → 재수정 → 테스트 → 최종 판단.

1. 요청이 조사/설명/리뷰인지 실제 구현인지 먼저 구분한다. 조사 요청이면 취합/최종 판단에서 끝내며 코드를 수정하지 않는다.
2. 대상 프로젝트의 지침, 환경 문서, 현재 Windows Git 상태를 확인한다. 메인이 최소한의 초기 탐색으로 영향 시스템과 완료 조건을 정한다.
3. 자동 적용 원칙에 따라 코드 조사·리뷰·기능/버그 작업의 필요한 독립 조사·검토를 위 역할로 실제 위임한다. 사용자의 반복 요청을 기다리지 않는다. 예외에 해당해 생략하면 이유를 짧게 밝힌다.
4. 각 하청에는 프로젝트, 질문, 범위/관련 경로, 현재 가설, 확인할 근거, 기대 산출물, 읽기 전용 제한을 포함한다.
5. 독립된 검토는 병렬로 시작한다. 결과를 기다리는 동안 메인은 계획/검증 시나리오를 준비할 수 있지만 해당 검토 대상 구현은 취합 후 결정한다.
6. 결과의 사실/추정, 중복, 모순을 정리하고 실제 파일·헤더·로그로 확인한다. 다수결로 구현을 결정하지 않는다.
7. 승인된 기능 범위의 수정은 메인만 한다. Docs/AI/Build.md의 빌드 → 오류 분석 → 관련 수정 → 재빌드 → 필요한 테스트를 수행한다. 새 변경/실패 없이 통과한 검증을 반복하지 않는다.
8. 막연히 계속 수정하지 않는다. 어려운 문제면 가설/로그와 함께 ue_deep_reviewer를 호출한다. 완료된 하위 스레드를 닫아 동시 한도를 지킨다.
9. 최종 보고: 실제 위임한 역할/모델/추론 설정과 확인 한계, 주제별 결론, 채택·보류 근거, 수정 파일, 브랜치, 빌드/테스트와 로그, 미검증 항목.
10. 모델/역할을 사용할 수 없으면 실패 사실을 보고한다. 요청된 모델을 다른 모델로 조용히 대체하지 않는다.

## 동적 하청 구조 (주제와 인원은 요청별 결정)
Astra Medium
├─ ue_senior_reviewer / Sol Medium A: 현재 요청의 검토 주제 A
├─ ue_senior_reviewer / Sol Medium B: 독립된 검토 주제 B (필요한 경우)
└─ ue_research_scout / Luna High: 현재 요청에 필요한 탐색·근거 수집
          ↓
Astra가 근거 확인 및 결과 통합 → 실제 수정 결정

대화 기능 작업이라면 검토 주제에 DialogueSubsystem 구조나 SaveGame 로직, 조사 대상에 GameplayTag 사용 위치가 포함될 수 있다. 이는 특정 요청에 대한 예시이며 다른 기능에 그대로 적용할 고정 작업 목록이 아니다.

## 권한 및 요청 경계
- 메인만 파일 수정, Windows Git 변경, 빌드/테스트, 에디터 조작을 담당한다.
- 서브에이전트는 읽기 전용 기본값 + 명시적 작업 지침을 따른다. 하위의 추가 하청은 끈다.
- 부모의 런타임 권한이 하위 sandbox 기본값보다 우선할 수 있다. MCP/GUI 권한까지 자동으로 차단한다고 보장하지 않는다.
- 저장 형식 변경, 기존 에셋 삭제/이름 변경, 엔진 변경/새 외부 플러그인, 승인 범위 밖 재설계는 사용자 확인.
- 기존 미커밋 변경을 보존한다. 커밋/push/merge는 요청 범위를 따른다.
- DialogueMaker의 PLANS.md 및 연출 작업의 ImageProduction.md 규칙도 유지한다.

## 설정과 적용
프로젝트 .codex/config.toml과 .codex/agents/*.toml을 새 세션에서 로드한다. 부모 폴더에도 같은 팀이 있어 두 프로젝트를 함께 조정할 수 있다.
프로젝트 신뢰 여부나 관리 정책으로 설정이 무시될 수 있으므로 /status 및 실제 하위 스레드에서 확인한다.
현재 세션은 파일 변경으로 모델/추론이 자동 변경되지 않는다.
