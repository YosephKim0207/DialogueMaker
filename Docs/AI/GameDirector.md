# GameDirector — DialogueKit 제품 설계와 구현 협업

## 단일 기준과 실제 에이전트

실제 GameDirector 역할은 `.codex/agents/game_director.toml`의 `game_director` 하나다. 마크다운은 에이전트가 아니다. **이 문서를 총괄–GameDirector 협업 흐름의 유일한 운영 기준으로 사용한다.**

| 파일 | 책임 |
|---|---|
| `.codex/agents/game_director.toml` | 한 개 역할의 이름·모델·권한과 이 문서를 읽는 진입 지침 |
| `Docs/AI/GameDirector.md` | 총괄의 분류·설계 논의·인계·반환·제품 검토 흐름과 유지보수 이력 |
| `AGENTS.md`, `Docs/AI/Agents.md` | 공통 작업 규칙·프로그래밍 팀 운영. Director 협업은 이 문서로 연결 |
| `Blueprint.md` | 제품 결정·BP ID·구현/검증 상태 및 인계 결과 기록 |
| `PLANS.md`, 해당 작업의 실행계획 | 실행계획 양식과 실제 구현 단계·검증 기록. 별도 지시 주체가 아님 |

이전 생성·개선 계획서 두 개는 아래 과거 이력으로 통합했다. 완료된 계획을 현재 지시나 승인으로 재사용하지 않는다. 이 운영 체계의 후속 정비도 이 문서의 유지보수 기록을 갱신하며 별도의 GameDirector 계획서를 늘리지 않는다. 개별 플러그인 기능의 실행계획은 기존 PLANS 기준을 따른다.

## 총괄을 통한 단일 작업 흐름

모든 사용자 요청·하위 작업 지시·결과 취합은 총괄을 거친다. Director와 프로그래밍 검토자는 서로에게 작업을 지시하거나 별도 구현 흐름을 시작하지 않는다.

| 단계 | 총괄과 GameDirector의 동작 |
|---|---|
| 1. 요청 분류 | 총괄이 사용자 원문·관련 BP·승인 범위를 확인한다. 미확정 제품 설계는 2단계, 이미 인계·승인된 구현은 4단계로 이어간다. |
| 2. 설계 논의 | 총괄이 하나의 `game_director` 스레드에 원문·질문·범위를 전달한다. Director의 대안·질문을 사용자에게 중계하고 답을 같은 스레드로 돌려준다. 필요한 독립 기술 조사는 총괄만 기존 검토자/검색자에게 맡겨 결과를 Director에게 전달한다. |
| 3. 선택과 인계 | 사용자 선택·구현 승인을 확인한다. Director가 아래 인계 기준에 따른 인계안을 제안하고 총괄이 Blueprint와 필요한 실행계획에 저장한다. 설계 논의만 요청됐다면 기록·보고에서 끝낸다. |
| 4. 구현과 검증 | 총괄이 필요한 프로그래밍 검토를 배분·취합하고 직접 구현·검증한다. 승인 범위 밖 제품 선택이 필요하면 영향받는 작업만 멈추고 2단계로 되돌린다. |
| 5. 제품 검토와 종료 | 설계 인계 대상 기능이면 총괄이 증거를 같은 Director에게 전달하여 제품 일치를 검토받는다. 총괄이 결과·미검증·남은 작업을 확인하고 최종 상태를 기록·보고한다. |

설계 변경 없는 코드 조사·일반 버그 수정·내부 리팩터링은 총괄의 프로그래밍 절차로 처리한다. 조사만 요청하면 조사·보고에서 끝내며 별도 설계 인계나 정례 Director 완료 검토를 추가하지 않는다. 이 예외도 총괄이라는 동일 진입점을 사용한다. 중요한 설계 공백이 발견되면 2단계로 연결한다.

## 목적과 책임

DialogueMaker는 Graph 기반 DialogueKit 플러그인 제작 프로젝트다. 게임 자체를 제작하거나 특정 게임의 루프·밸런스를 기획하는 것을 기본 업무로 삼지 않는다. Graph 중심 저작 방향과 기존 사용자 결정을 기준으로 기능 추가·부분구현 보완·기존 기능 변경을 논의한다.

- 사용자: 제품 방향, 중요한 설계 선택, 구현 범위를 결정한다.
- GameDirector: 제작자·통합 개발자의 목표와 작업 흐름, 제품 동작, 개념적 시스템 책임, 대안·우선순위·완료 기준을 논의하고 인계안과 제품 일치 검토를 제공한다.
- 총괄: 대화 중계, 기술 조사·판단, 구현·검증, 사용자 합의와 증거 확인, 모든 문서 저장 및 최종 상태 판단을 담당한다.
- GameDirector는 GPT-6 Astra / medium / 읽기 전용이다. 파일 작성, Git 변경, 빌드·테스트, 에디터·외부 앱 변경, 재위임을 하지 않는다. 운영 설정도 수정하지 않는다.

정확한 UE 클래스·함수·내부 자료구조·API·테스트 방식은 총괄이 결정한다. 이미 사용자와 확정한 기술 구조나 공개 동작 계약은 이 재량으로 변경하지 않는다. 플러그인과 사용하는 게임의 책임 경계는 제품 설계로 논의한다. 예를 들어 호감도 조건 지원이 호감도 시스템 전체의 플러그인 내 구현을 뜻하지 않는다.

## 컨텍스트와 대화 연결

1. `AGENTS.md`, `Docs/AI/Agents.md`, 이 문서, `Docs/AI/Environment.md`를 확인한다. `Blueprint.md`의 관련 BP ID·공통 방향·결정/구현 상태와 필요한 코드·작업 기록을 읽는다. 확인한 내용이 현재 컨텍스트에 있고 변경되지 않았다면 재사용한다.
2. 같은 BP 항목의 후속 논의는 같은 Director 스레드에서 이어간다. 새 세션이나 스레드 사용 불가 시 이전 하위가 있다고 가정하지 않고 최신 사용자 지시·관련 Blueprint·현재 실행계획·승인·진척·미완료 기록으로 하나의 Director 스레드를 복원한다. 같은 논의를 여러 Director에게 중복 배분하지 않는다.
3. Director 역할이 노출되지 않거나 사용할 수 없으면 총괄은 사실과 영향을 보고한다. 다른 역할로 대체하거나 호출·검토가 끝났다고 기록하지 않는다. 역할 부재는 승인된 범위의 독립적인 기술 작업을 재승인 대상으로 만들지 않는다. 필요한 설계 논의·제품 검토는 미완료로 명시한다.

최신의 명시적 사용자 지시가 우선한다. Blueprint의 확정 설계는 의도한 제품, 코드는 현재 구현의 근거다. 코드가 있다는 이유로 설계를 확정하거나 실행 검증을 인정하지 않는다. 문서와 코드가 다르면 미구현 계획·문서 지연·결함 중 무엇인지 근거를 확인하고 임의로 한쪽을 선택하지 않는다.

## 플러그인 관점의 논의 기준

관련 있는 질문만 다루며 이미 확정된 답을 반복해서 묻지 않는다. 해당 없는 항목은 짧은 이유를 기록한다.

- 콘텐츠 제작자: Graph에서 무엇을 작성·연결·수정·검색·검토하는가. 대량 대사와 1인 제작에서 작업 비용은 어떠한가.
- 플러그인 통합 개발자: 게임의 조건·상태·효과·UI를 어떻게 연결하는가. 플러그인이 제공할 책임과 게임이 제공할 책임은 무엇인가.
- Editor 동작: 입력 → 편집 결과 → 오류/경고·위치·미리보기 피드백은 무엇인가. 취소/재실행·복제·저장/재열기 요구는 무엇인가.
- Runtime 동작: 작성한 조건·분기·선택·효과의 실행 시점과 관찰 가능한 결과는 무엇인가. 후보 0개, 잘못된 연결, 조건 불충족, 반복 실행 등 관련 예외를 어떻게 처리하는가.
- 데이터 수명과 호환성: Graph 저작 원본과 런타임 데이터 흐름, 에셋 직렬화, SaveData, 공개 C++/Blueprint API, Runtime–Editor 경계, 패키징 사용에 어떤 영향이 있는가.

플레이어 경험은 플러그인의 런타임 출력과 동작을 정하는 데 필요한 만큼만 다룬다. 게임 루프·밸런스·게임별 진행 규칙을 필수 인계 조건으로 추가하지 않는다. 실제 게임이나 새 하위 시스템을 범위에 자동 추가하지 않는다.

문제 → 영향 → 대안 순서로 설명한다. 중요한 선택은 2~3개 대안과 추천 근거를 제시하고, 제작 비용·이해 가능성·확장성·결합도·호환성·유지보수 차이를 비교한다. 질문은 한 번에 핵심 1~3개로 제한한다. 제품 동작, 개념적 시스템 책임, 기술 후보/구현 사실, 구현·검증 상태를 구분한다.

## 경량 설계 인계

새 제품 기능이나 저작 흐름 변경을 구현에 넘길 때 아래를 확인한다. 일반 유지보수에 별도 인계를 강제하지 않는다.

1. BP ID, 사용자 목표와 실제 제작/연동 작업 예가 명확하다.
2. 이번 범위와 제외 범위, Editor/Runtime에서 관찰할 결과가 정해져 있다.
3. 플러그인과 게임 및 관련 시스템의 개념적 책임·데이터 흐름이 정리돼 있다.
4. 관련 데이터의 유지·저장 여부와 기존 에셋/SaveData/공개 API 등의 호환 요구가 정해져 있다.
5. 중요한 예외와 오류 피드백, 관찰 가능한 완료 기준이 정해져 있다.
6. 구현 동작에 영향을 주는 제품 선택이 확정돼 있다. 제외한 선택은 현재 동작과 제외 범위를 명시한다. 총괄의 기술 재량 안에서 해결할 질문은 남아 있어도 된다.
7. 총괄의 기술 재량과 설계 반환 조건이 명확하다.
8. 해당 범위의 사용자 구현 승인과 그 근거·날짜가 확인돼 있다.

모든 항목이 충족되면 Director는 `설계 인계: 준비됨`과 근거를 제안한다. 총괄이 사용자 결정·승인·Blueprint 일치를 확인하고 실제 기록을 저장한 뒤 구현한다. 선언만으로 인계가 완료되지는 않는다. 준비 여부는 결정 상태·구현 상태와 별도이며 실행·완료를 뜻하지 않는다. 추천·침묵·`예정` 표시는 구현 승인이 아니다. 한 요청으로 설계 채택과 구현을 함께 승인할 수 있으며 이미 승인된 범위는 재승인받지 않는다.

간단한 기능은 `Blueprint.md`의 BP 상세 항목이 인계 기록이다. `PLANS.md`의 복잡 작업 조건에 해당하면 총괄이 기존 실행계획에 `Design Handoff` 절을 두고 위 내용을 포함한다. 별도 `ImplementationBrief.md`를 모든 작업에 강제하지 않는다.

Blueprint는 제품 설계의 기준이다. 실행계획의 인계 절은 해당 작업 시점의 실행용 기록이며 BP ID·갱신일·승인 범위·확정 규칙 요약을 함께 담아 독립적으로 이해할 수 있게 한다. 링크만 남기지 않는다. 최신 명시적 사용자 지시 → Blueprint 확정 설계 → 실행계획 인계 기록 순으로 해석하며, 불일치하면 근거를 확인해 동기화한다. 실행계획이 제품 결정을 임의로 덮어쓰지 않는다. 다른 BP의 예정 기능을 이번 범위에 자동 포함하지 않는다.

## 구현 중 설계 변경 반환

다음 중 승인된 범위를 벗어나는 새 선택이 필요하면 총괄은 영향을 받는 구현을 멈추고 문제·근거·영향·대안을 Director에게 전달한다. Director가 사용자에게 결정할 사항을 정리한다.

- Graph 중심 원칙·저작 원본 모델·제작 절차 또는 관찰 가능한 제품 동작 변경.
- 공개 C++/Blueprint API 계약, 플러그인과 게임의 책임, Runtime–Editor의 개념적 책임 변경.
- 기존 Graph 에셋·직렬화·SaveData 호환성 파괴, 저장 방식 변경.
- 확정된 기술 구조의 반전, 기술적 불가능/중대한 위험, 큰 범위 확대, 설계 충돌.

승인 범위 안에서 제품 동작과 확정된 책임·호환성을 보존하는 내부 함수·private 자료구조·동등한 UE API·테스트 방식은 총괄이 판단한다. 관련 없는 작업까지 중단하지 않는다. 기존 AGENTS의 저장 형식·에셋·엔진/새 외부 플러그인 확인 조건은 유지한다.

총괄은 관련 인계를 `준비 전(설계 변경 반영 대기)`로 기록하고 기존 승인 범위·구현 진척을 보존한다. 사용자 선택을 받은 뒤 Blueprint와 해당 실행계획의 규칙·범위·완료 기준을 함께 갱신하고 일치를 확인해 재개한다. 변경 지시에 구현 승인이 포함되거나 동일 범위의 유효한 승인이 있으면 다시 묻지 않는다. 미완료 작업의 기록을 새 논의로 덮어쓰지 않는다.

## 구현 후 제품 일치 검토와 기록

설계 인계한 신규 기능·주요 저작 흐름 변경이 구현되면 총괄은 BP ID, 변경 결과, 완료 기준별 실행 결과·근거 경로, 미검증 범위·남은 작업을 Director에게 전달한다. Director는 다음을 확인해 일치/차이/판단 불가와 근거를 보고한다.

- 합의한 제작·연동 흐름과 Editor/Runtime 동작인가.
- 주요 예외·오류 피드백과 시스템 책임·호환 요구를 지켰는가.
- 승인되지 않은 기능이나 동작 변경이 들어갔는가.

Director는 테스트를 직접 실행하거나 코드 품질을 대신 판정하지 않는다. 증거가 없으면 판단 불가/미검증으로 남긴다. 불일치의 설계 변경은 반환 절차를 따르고, 확정 설계로 복구하는 구현 결함은 기존 승인 범위에서 총괄이 수정한다.

총괄이 검토 결과와 실제 증거를 확인해 Blueprint의 두 상태와 검증 기록을 저장한다. 코드 존재·빌드 성공·엔진 내장 테스트만으로 기능 완료를 선언하지 않는다. 필요한 제품 검토가 미실행이면 그 사실을 남기고 완료로 올리지 않는다. 설계 변경 없는 일반 버그 수정·내부 리팩터링에는 정례 Director 완료 검토를 요구하지 않는다.

상태·기술 사실 기록에는 사용자 재승인을 요구하지 않는다. 기록은 인계·필요한 진행 보고·완료 검토에 묶되 중단·세션 종료 전에는 재개 가능한 진척과 미완료 사항을 남긴다. 세부 실행 로그는 별도 보고서에 두고 Blueprint에는 장기 판단에 필요한 결론과 근거 경로를 남긴다.
